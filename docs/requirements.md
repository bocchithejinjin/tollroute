# 要件定義書：高速料金・予算内最速ルート検索アプリ

2026-11-23 時点（元は Claude Docs で作成。リポジトリでは Markdown で管理する）

## 1. 目的と背景

出発地と目的地の住所、高速代の予算を入力すると、**予算内でいちばん早く着く「乗る IC・降りる IC」の組み合わせ**を示す Web アプリを作る。

- 解きたい問題：高速を全区間使うと高く、使わないと遅い。「3,000 円まで払うなら、どこからどこまで乗るのが最適か」を、すぐに知りたい。
- 副次的な目的：Django ハンズオン教材の新しい題材にする。前回の題材（アニメ放送表ダッシュボード）から置き換え、GeoDjango・PostGIS・外部サービスとの連携・ナビ連携を学べるようにする。
- 使うデータは、OpenStreetMap（OSM）などのオープンデータを中心にする。

## 2. 対象範囲

**全国の高速道路と有料道路**を対象にし、**普通車の ETC 料金を、曜日と時間帯による割引や料金の違いまで含めて**計算する。自分で実際に使うアプリとして作る。

| 項目 | 含める | 含めない（後の版で検討） |
| --- | --- | --- |
| 道路 | NEXCO 東・中・西日本、首都高速、阪神高速、本州四国連絡高速、名古屋高速、福岡北九州高速、広島高速、地方道路公社などの有料道路 | フェリー |
| 車種 | 普通車 | 軽自動車等、中型車、大型車、特大車（車種を切り替えられるデータの持ち方にはしておく） |
| 料金 | ETC 料金。ETC が使えない有料道路は現金料金で計算し、画面で分かるようにする | ETC を使わない場合の料金 |
| 割引・時間帯別の料金 | 休日割引、深夜割引、東京湾アクアラインなどの時間帯別の料金、各社の時間帯割引。適用しない日（年末年始など）も扱う | 大口・多頻度割引、ポイント還元、周遊プランなどの申し込みが必要な割引、障害者割引 |
| 時刻 | 出発日時を入力し、各 IC を通る時刻を見積もって割引を判定する | 渋滞予測 |
| 高速の使い方 | 1 回乗って 1 回降りる。その間に運営会社をまたぐのはよい（例：首都高 → 東名） | 途中で降りて一般道を通り、また乗る（2 区間以上）。一時退出の特例 |

## 3. 利用シナリオと画面

代表的な使い方：土曜日の朝 7 時に**横浜駅**を出て**新宿駅**へ、高速代 1,000 円までで行く。東名と首都高、圏央道と中央道、第三京浜・横浜新道と一般道（無料の保土ヶ谷バイパスを含む）など、運営会社をまたぐ選択肢があるので、動作確認の基本の例にする。

1. 検索画面で、出発地の住所、目的地の住所、**出発日時**（初期値は現在）、予算（円）を入力する。
2. 住所が見つからない、または候補が複数あるときは、候補を一覧で示して選ばせる。
3. 結果画面に、**予算内のおすすめを最大 5 ルート**並べる。ルートごとに次を表示する。
   - ラベル（最速・いちばんお得・安さ重視など）
   - 所要時間と到着時刻、高速代、一般道だけより何分早いか、**お得度**（一般道だけより 1 分早く着くのに何円かかるか）
   - 道順（一般道で出発地 → 乗る IC、道路ごとの区間と通過時刻、降りる IC → 目的地）
   - 料金の内訳（運営会社ごとの金額と、適用した割引）
   - **Google マップで開くボタン**（乗る IC・道路が変わる JCT・降りる IC を経由地にする）
4. あわせて、予算と所要時間のグラフ、すべての候補の一覧、一般道だけの所要時間（基準）を表示する。地図は表示しない（ナビアプリに任せる）。
5. 出発時刻をずらすと安くなるときは、そのことを知らせる（例：「30 分遅く出ると深夜割引が適用され、520 円安くなります」）。
6. 予算や出発日時を変えて、もう一度検索できる。

画面の金額はすべて説明のための例。画面は AdminLTE 3 のダッシュボードの形にする。そのほかに、IC の一覧画面と、Django の管理画面（IC・区間・料金・割引データの修正用）を用意する。

## 4. 機能要件

| ID | 機能 | 内容 |
| --- | --- | --- |
| F1 | 住所から座標への変換 | 日本の住所（番地まで）や駅名を緯度・経度に変える。jageocoder を使い、自分の PC だけで処理する。どの細かさまで当たったか（町丁目・番地など）も返す。駅名は OSM の駅データで引く |
| F2 | 一般道の所要時間 | 出発地から各 IC、各 IC から目的地までの所要時間を、有料道路を除外してルート検索エンジンで求める。複数地点をまとめて問い合わせる |
| F3 | 高速道路網 | 全国の IC・JCT・料金所と、その間の区間（距離、所要時間、運営会社、料金の区分）をグラフとして持つ。「この IC は東京方面にしか乗れない」といった、乗り降りできる方向の制限も持つ |
| F4 | 料金の計算 | 通る区間を運営会社ごとに区切り、会社ごとの料金の決め方で計算して合計する（詳細は 5 章） |
| F5 | 割引・時間帯別の料金 | 出発日時と所要時間から各 IC を通る時刻を見積もり、休日割引・深夜割引・時間帯別の料金を判定する。祝日と、割引を適用しない日のカレンダーを持つ |
| F6 | 最適な組み合わせの探索 | 出発地・目的地の周りの IC を候補にし、乗る IC と降りる IC の組み合わせごとに、高速道路網の中で「料金と時間のどちらかが優れる経路」をすべて求める。その中から予算以内で最短のものを選ぶ。「高速を使わない」も候補に含める。予算内の候補から、最速・いちばんお得・安さ重視などの観点で最大 5 ルートを選ぶ |
| F7 | 出発時刻の提案 | 出発を前後 2 時間の範囲でずらすと安くなる場合に、その時刻と差額を示す |
| F8 | 予算と所要時間の関係 | 「これより安くて速い候補がない」組み合わせだけを残し、グラフにする |
| F9 | ルート情報とナビ連携 | 道順を文字で示し、通過地点を Google マップ（Maps URLs）に渡すリンクを作る |
| F10 | 料金・割引データの管理 | 区間・料金表・割引の規則に**有効期間**を持たせ、料金改定や割引の制度変更に対応する。Django の管理画面で直せる。初期データはコマンドで取り込む |
| F11 | 料金の照合 | 各社の公式の料金検索で調べた値を登録しておき、計算結果との差を一覧で見られる |
| F12 | 検索履歴 | 直近の検索条件を保存し、再検索できる |

## 5. 料金計算の仕様

料金は「**運営会社ごとの基本料金**」を求め、そこに「**割引・時間帯別の規則**」を重ねて計算する。会社ごとに料金の決め方が違うため、計算の部品を会社ごとに分け、差し替えられるようにする。下の表の仕組みと数字は記憶によるおおよそのもので、**すべて実装の前に各社の公式ページで確かめる**。

### 5.1 運営会社ごとの基本料金

| 運営会社 | 料金の決め方（概要） | 注意する点 |
| --- | --- | --- |
| NEXCO 東・中・西日本 | 利用 1 回ごとの定額＋ 1km あたりの単価 × 距離。長距離は割引。NEXCO どうしを続けて使うと 1 回の利用として計算 | 大都市近郊区間は単価が高い。長いトンネルを含む区間や、固定金額の区間など、例外が多い |
| 首都高速 | 距離に応じた料金（下限と上限あり） | 首都圏では、通った経路ではなく**入口と出口で料金が決まる**仕組みがある（遠回りしても料金が同じになることがある） |
| 阪神高速 | 距離に応じた料金（下限と上限あり） |  |
| 本州四国連絡高速 | 距離に応じた料金 | 橋の区間は料金の仕組みが別 |
| 名古屋高速、福岡北九州高速、広島高速 | 会社ごとに距離制または均一料金 | 要確認 |
| 東京湾アクアライン | 区間ごとの固定料金 | **曜日と時間帯で ETC 料金が変わる**（時間帯ごとの金額と対象の曜日は要確認） |
| 地方道路公社などの有料道路 | 区間ごとの固定料金が多い | ETC が使えない道路がある。数が多く、無料化もある |

運営会社をまたぐときは、会社ごとに計算して合計する。ただし、またいだときの特別な扱い（乗り継ぎの特例など）がないかも確かめる。

### 5.2 割引と時間帯別の料金

| 規則 | 条件（概要） | 判定に必要なこと |
| --- | --- | --- |
| 休日割引（NEXCO など） | 土日祝に、大都市近郊区間以外を走ると安くなる。年末年始・お盆・GW などに適用しない日がある | 入口または出口を通る日、区間ごとの「大都市近郊かどうか」、適用しない日の一覧 |
| 深夜割引（NEXCO など） | 深夜の時間帯に高速を走っていると安くなる | 各 IC を通る時刻。**制度の見直し（対象の時間帯、割引がかかる距離の範囲）が進んでいるので、現在の制度を必ず確かめる** |
| 時間帯別の料金（アクアラインなど） | 曜日と時間帯で料金が変わる。期間を区切った取り組みとして実施されることがある | 料金所を通る時刻、実施期間 |
| 各社独自の割引 | 首都高・阪神高速などの時間帯ごとの割引 | 要調査 |

割引は、「どの区間に」「どの日・時間帯に」「何割引きまたは何円にするか」「有効期間」をデータとして持ち、コードを直さずに制度の変更に対応できるようにする。割引どうしが重なるとき（例：休日の深夜）は、割引率の高い方だけを適用するような、重なり方の規則も確かめて実装する。

### 5.3 料金データの入手

全国の正確な料金を無料で返す、公開のデータや API は確認できていない。そこで、実装の前に次を調べて方針を決める。

1. **有料 API**（NAVITIME など）：全国の ETC 料金、割引、出発日時の指定に対応しているか。個人で使うときの費用。結果を保存して使い回してよいか。
2. **公開資料**：各社・高速道路機構・国交省が公開している料金表や料金の決め方の資料。どこまで機械的に取り込めるか。
3. **公式の料金検索**（ドラぷらなど）：照合のために手作業で使う。自動での取得はしない。

有力な方針は次の 2 つで、どちらでも差し替えられる設計にする。

- **A：自前の料金エンジン**。無料で、仕組みを学べる。全国分のデータを作り、料金が改定されるたびに直し続ける必要がある。NEXCO → 首都高 → アクアライン → 阪神高速 → その他の順に広げる。
- **B：有料 API**。全国をすぐに網羅できるが、費用がかかり、使えるかは利用規約次第。

### 5.4 照合方法

- 運営会社ごとに代表的な区間を選び、公式の料金検索で調べた値をテストデータにする。
- 同じ区間を、平日の昼、土曜の昼、深夜、割引を適用しない日（例：年末年始）、アクアラインの時間帯ごとなど、**曜日と時間帯の組み合わせ**で確かめる。
- 横浜駅〜新宿駅で使う区間（東名、首都高、第三京浜、横浜新道、圏央道、中央道など）を最初に照合する。
- 目標は公式の料金と 1 円もずれないこと。ずれた区間は、画面に「概算」と表示する。

## 6. 非機能要件

| 分類 | 要件 |
| --- | --- |
| 応答時間 | 1 回の検索で結果が出るまで 5 秒以内。出発時刻の提案（F7）は後から表示してもよい |
| 料金の正確さ | 公式の料金と一致させることを目標にする。照合できていない区間、ずれが分かっている区間は「概算」と表示する。料金データの確認日も画面に出す |
| 所要時間 | 渋滞を含まない目安として表示する。割引の時間帯の境目に近いときは「渋滞すると割引が外れるおそれがあります」と注意を出す |
| 障害時 | ルート検索エンジンが応答しないときは、一定時間で打ち切り、「ルート検索サービスに接続できません」と表示する |
| プライバシー | 住所は外部のサービスに送らない。有料 API を使う場合も、送るのは IC の組み合わせと日時だけにする |
| ライセンス | OSM のデータと地図には「© OpenStreetMap contributors」を表示する（ODbL）。地図タイルは配信元の利用規約を守る |
| 動作環境 | 自分の PC（メモリ 16GB）の Dev Container だけで動かす。**インターネットには公開せず、Tailscale（自分の機器どうしだけの私的なネットワーク）でスマホから使う**。app、PostgreSQL（PostGIS 入り）、ルート検索エンジンの 3 つのコンテナ |
| ルート検索エンジン | 日本全国の道路網の下準備は、OSRM だと 16GB では足りないおそれがある。OSRM と Valhalla で実際に試し、使うメモリと時間を測ってから選ぶ。下準備は 1 回だけなので、時間がかかってもよい |
| ディスク | OSM の日本全国のデータ、ルート検索用のデータ、jageocoder の辞書で、数十 GB を使う見込み。実測して記録する |
| テスト | 料金計算、割引の判定、組み合わせの探索は、ルート検索エンジンなしで動く単体テストで確かめる |

## 7. 技術構成とデータ

前回の構成（Django 5.2、AdminLTE 3、Bootstrap 4.6、PostgreSQL、Dev Container）を引き継ぎ、PostGIS、ルート検索エンジン（OSRM か Valhalla）、jageocoder を加える（地図は表示せず、ナビアプリに連携する）。

構成: ブラウザ → Django アプリ（GeoDjango。画面・API、住所の変換、料金計算、組み合わせ探索）→ PostgreSQL + PostGIS と OSRM（ルート検索）。OpenStreetMap データは準備のときにだけ使う。

住所の変換とルート検索は自分のコンテナで動かす。OSM データは準備のときにだけ使い、検索のたびには取りに行かない。料金を有料 API から取る場合（5.3 の B）は、「料金計算」の部品だけを差し替える。

**データモデル（案）**

| モデル | 主な項目 | 用途 |
| --- | --- | --- |
| Operator（運営会社） | 名前、料金の決め方の種類（対距離、距離制＋上限、固定など）、ETC が使えるか | 料金計算の部品を選ぶ |
| Interchange（IC・JCT・料金所） | 名前、路線、キロポスト（km）、位置（PointField）、種類、乗り降りできる方向 | 乗る IC・降りる IC の候補 |
| Segment（区間） | 始点、終点、運営会社、距離（km）、料金の区分（普通・大都市近郊など）、所要時間（秒）、形（LineStringField） | 高速道路網のグラフ |
| FareTable（料金表） | 運営会社、入口、出口、車種、料金（円）、有効期間 | 固定料金や「入口と出口で決まる」料金 |
| FareRate（単価） | 運営会社、区分、定額部分、km 単価、下限・上限、長距離の割引率、端数の扱い、有効期間 | 距離に応じた料金 |
| DiscountRule（割引・時間帯別の料金） | 名前、対象の区間、曜日、時間帯、判定に使う時刻（入口・出口・走行中）、割引率または金額、優先順位、有効期間 | 休日割引、深夜割引、アクアラインなど |
| CalendarDay（カレンダー） | 日付、祝日かどうか、割引を適用しない日かどうか | 休日の判定 |
| FareCheck（料金の照合） | 入口、出口、日時、公式の料金（円）、確認日 | 計算のずれをテストで確かめる |
| SearchHistory（検索履歴） | 出発地と目的地の住所・座標、出発日時、予算（円）、検索日時 | 再検索 |

## 8. 進め方と未決事項

まず自分で使うアプリとして動くものを作り、その後でハンズオン教材に仕立てる。教材のゴールは前回と同じく「このアプリの PR をレビューできるようになること」。

1. **探索の方法を比べる**：複数のアルゴリズムを試し、正しさと速さをテストで比べて採用するものを決める（結果は 9 章に記録する）。
2. **料金と割引の中心部分**：料金計算（F4）、割引の判定（F5）、探索（F6）を作る。横浜駅〜新宿駅で使う区間から始め、公式の料金と照合する。
3. **ルート検索と住所**：ルート検索エンジンと jageocoder をコンテナで動かし、F1・F2 をつなぐ。
4. **画面**：AdminLTE の検索画面・結果画面、地図とグラフ（F7〜F9）。
5. **全国へ広げる**：運営会社ごとに料金データを整えて照合する（5.3）。
6. **教材化**：章立て、レビュー演習、チェックポイントを作る。

**決まったこと**（2026 年 11 月 23 日）

- 対象は日本全国の高速道路と有料道路。ETC 料金で、割引と時間帯別の料金も正確に扱う。
- 動作確認の基本の区間は横浜駅〜新宿駅。
- 開発用 PC のメモリは 16GB。インターネットには公開せず、自宅の PC で動かして Tailscale でスマホから使う（2026-11-23 決定。手順は \`docs/remote-access.md\`）。将来ほかの人にも使ってもらう場合は、サーバー 1 台にまとめるか、Vercel（画面と API）＋別サーバー（ルート検索・住所辞書）にする。

**途中で決めたこと・分かったこと**

- 料金データは自前で整える（A）。NAVITIME の API は結果の保存が規約で禁止と読め、無料枠は月 500 回のため、照合用にとどめる。
- 背景地図は使わず、ナビアプリに連携する（利用者の要望）。
- 2026-11-24、所有者の判断で、経路の妥当性を確かめるために Google Routes API を使うことにした（それまでは「外部 API は使わない」）。Google だけでは「全部高速」か「高速なし」の候補に偏るため、自作エンジンの案を Google で確かめるハイブリッド方式にした。
- 料金制度の調査結果は `docs/research-fares.md`（未確認の点 14 個もそこに記録）。
