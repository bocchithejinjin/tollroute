# 時刻で料金が変わる道路網の厳密探索

## 推奨方針

待機なし・再訪可の多目的ラベル法を維持し、**目的地までの時間・料金下限による枝刈りと、将来の料金判定地点に絞った支配判定**を組み合わせる。まず下限と完成経路で探索範囲を狭め、次に首都高・料金所のように必要な料金状態が小さいプールから時刻の異なるラベルを比較する。NEXCO は料金状態を検証できた範囲から対応する。全国規模で数秒以内という目標は実測で判定する。

### 厳密解の範囲

- 固定の出発日時、入口・出口 IC 候補と一般道所要時間、固定の有向区間所要時間、現在の料金モデルを入力とする。現地での待機はなし。その場での U ターンと入口＝出口でのラン終了を禁止し、それ以外の再訪を認める。ランは同じ料金プールの連続利用を指す。
- [総当たり](../engine/brute.py)と同じ `(到着までの所要時間, 割引後料金)` の集合を返す。同値の経路は、現行 `pareto` と同様に代表を一つ保持する。一般道のみの所要時間を `T` とすると、料金が非負なら `T` より遅い経路は一般道案に支配される。`T` ちょうども比較に含める。予算指定時は同じ予算内に限って比較する。
- 区間時間は有限かつ正、一般道時間は有限かつ非負とする。これで `T` 内の走行区間数は有限になる。ゼロ時間の区間を導入する場合は、ゼロ時間閉路に対する停止性を別途証明する。料金状態はプールごとの加算を前提とする。ランをまたぐ割引を実装した場合は、料金状態と下限を再設計する。

## 1. 時間・料金の下限と完成経路で枝刈り

**時間下限 `h(v)`。** 出口候補から目的地へ、一般道の所要時間を重みにした仮想辺を張る。目的地から逆向きに Dijkstra を一度実行し、各ノードからの最小残り時間を求める。U ターン禁止、ラン終了条件を緩めたグラフで計算できる。合法な続きはすべて緩和グラフにも存在するため、`t + h(v) > T` なら枝を落とせる。`h(v) = ∞` は緩和しても到達不能を意味する。外部の `lower_bound_min` は同じ出口候補への正当な下限と確認できた場合に使う。

**料金下限 `g(L)`。** 最初は `closed + pending` にする。`closed` は終了済みラン、`pending` は現在の料金所ランで確定済みの金額。追加分が非負なら安全。次の下限は、足し合わせたときに同じ料金を二重に数えないようにする。

| 料金の種類 | 下限の作り方 |
| --- | --- |
| 現在の首都高・OD 表ラン | 同じプール内で到達できる合法終了点の上位集合を取る。終点候補と他プールへの切替点を含め、ラン入口と異なる点を対象とする。首都高は確定済みの料金版・割引状態、OD 表は対応表で料金を評価し、その最小値を使う。データが揃うまでは 0 円から始められる。 |
| 現在の NEXCO ラン | まず 0 円。次に、実装が取り得る最大割引率 `d_max` と逓減係数の下限 `α_min` を使う。非負単価・係数のもと、`税率係数 × (固定額 + α_min × 走行済みの単価付き距離の和) × (1 − d_max)` は割引後・丸め前の下限になる。各割引が基本額の `d_max` 以下で、最安の割引を一つ適用することを確認し、最後に実際の単調な円丸めを適用する。 |
| これから通過する料金所 | 料金所・方向ごとに `T` までの全料金状態で最小の通過額を各辺に設定し、仮想目的地まで逆向き Dijkstra を行う。時刻や経路制約を緩めた最短料金なので、現在ラン内と将来ラン内の未通過分にまとめて使える。確定済み `pending` は起点より前の通過だけを含む。料金関数の範囲を証明できない辺には 0 円を使う。 |

**完成経路による大域的な支配。** `B(L) = (t + h(v), g(L))` を下限の組とする。両下限を実現する続きが別々でも、どの合法な続きも両座標で `B(L)` 以上になる。実走行可能な完成案 `P` が時間・料金とも `B(L)` 以下なら、同値の代表を一つ残して `L` を捨てられる。予算指定時は `g(L) > budget` も枝刈りできる。ラン料金の上限は、それだけでは完成案の存在を保証しない。初期の完成案は一般道案と、時間最短などで得た候補を経路制約・全ラン料金まで再評価して作る。探索中に得た完成案も随時登録する。キューは `t + h(v)` を優先し、取り出し時にも最新の完成案で再判定する。

時間下限と料金所下限は、それぞれ二分ヒープで `O((V + E) log V)`。完成案を時間昇順かつ料金降順で保持すると、下限時刻以下で最も遅い完成案を二分探索して `O(log F)` で支配を調べられる。`F` は保持する完成案数。Python のリストなら挿入・削除で `O(F)` かかるため、必要になってからデータ構造を見直す。時間下限・大域支配からなら実装負担は小〜中。OD 下限は入口ごとの遅延計算・キャッシュを使い、全ノード対の料金表を無条件に生成しない。

## 2. 支配判定を将来の料金判定地点に絞る

### 比較の条件

早い `A` と遅い `B` は、同じノード、直前ノード、プール、ラン入口を持つものだけ比較する。これで `B` の合法な辺列を `A` からも走れる。続きの時間が固定なので、同じ出口を使えば `A` は `B` と同時か先に着く。次の二条件を満たした場合だけ `B` を捨てる。

1. 確定済み料金 `closed + pending` が `A ≤ B` で、現在ランの料金状態から、同じ続きを任意の合法点で締めても `A` の未確定分が `B` 以下と証明できる。
2. 同じ続きを走ったときに効く将来の料金判定が、両者で等しいか、`A` の方が安いと証明できる。最初は等しいときだけ支配する。

この二条件が成立すれば、`B` の完成案それぞれに対し、同額以下かつ同時刻以前の完成案を `A` から作れる。比較のために到着済みの時刻を動かす必要はない。同じ条件を満たす支配を繰り返してもこの関係は保たれる。

### 判定時刻の範囲

`B` の完成が `T` 以内になる続きだけを考える。料金判定イベント `x` までの最小時間の下限を `d_x(v)`、イベントから目的地までの最小残り時間の下限を `r_x` とする。その続きで起こる両ラベルのイベント時刻は、出発からの経過時間で `[A.t + d_x(v), T − r_x]` に含まれる。`B.t + d_x(v) + r_x > T` ならイベントは対象外。区間が空でなければ `depart` を足し、同じ料金判定が区間全体で成り立つか調べる。イベントの位置が出口なら出口ノード、料金所が辺の始点ならその辺を通る位置とし、後者の `r_x` にはその辺の走行時間も含める。

候補イベントをプール・判定種別でまとめ、緩和グラフで各グループへの逆向き多点 Dijkstra と、各グループから目的地までの `r_x` の最小値を用意する。異なるイベントで達成した最小値を組み合わせても範囲は広がる側なので安全。まず全グループを小さく固定し、到達不能や時間切れのイベントを除く。局所化が足りないグループだけ、方向や料金所単位に分ける。日にちが変わっても判定が同じなら同一区分として扱える。個別料金関数の境界が分からない場合は、異時刻間の比較を保留する。

ラン入口イベントを求める緩和グラフでは `(ノード, 直前のプール)` を頂点とし、初回進入とプールを切り替える辺だけを入口イベントとする。たとえば首都高から他プールに出た後の首都高への再流入は検査に含められる。同じ首都高プールの辺を連続して走る場合は入口イベントが発生しない。直前プールの候補は各ノードの流入辺にあるものと初期状態から生成する。

| 料金タイプ | 現在のランで保持する状態と、将来調べるイベント |
| --- | --- |
| 首都高 | 現在ランの料金版・深夜割引フラグを入口で確定。ラン入口が同じなら、同じ出口での料金も等しい。現在ラン継続中の 0 時・4 時や改定時刻は料金に影響しない。後続の首都高ランに入る時だけ、料金版と割引フラグを比較する。 |
| 時刻非依存の OD 表 | 入口・出口で料金が決まる。時間のイベントは不要。 |
| 料金所 | 過去の通過額は `pending` に加算済み。将来は料金所付き辺を通る時だけ、その方向での金額を比較する。アクアラインは時刻帯、休日切替と適用期間を反映する。 |
| 現行 NEXCO | 入口日の休日判定、入口時刻で選んだ制度、ランが既に 0〜4 時に重なったかを保持する。出口日の休日判定はランを締める時に評価する。まだ深夜帯に重なっていないランは、今後の走行中に 0 時を迎えるかで重なりが変わるため、ラン終了までの重なりを検証する。すでに重なっていれば、そのフラグは維持される。後続ランには入口と終了の両方が必要。全区分の料金計算に必要な距離状態も比較する。 |
| 見直し後の NEXCO 深夜割引 | 入口で制度を選び、対象辺と 22〜翌 5 時の重複で得た走行距離・時間を保持する。窓をまたいで走る辺では、窓の時刻と両端の相対位置で割引対象量が変わる。入口・出口の時間帯だけで同一視できない。初期版は、現在ランでこの制度が適用される場合、同時刻かつ同じ料金状態の場合だけ比較する。後続ランで有効になり得る場合も、異時刻での対象量の一致を証明できるまでは比較を保留する。 |

たとえば 23:50 に首都高へ入った二経路を、同じ直前ノードから 23:56 と 23:58 に同じ JCT へ着いた時点で比較する。残りが同じ首都高ランの出口と一般道だけなら、0 時をまたいでも同じ出口の料金は等しい。早い経路が支配できる。一方、両ラベルが 0 時前に JCT に着き、その先の料金所に一方だけ 0 時以降に着く場合は、現在時刻が同じ時間帯でも料金は変わり得る。

判定イベントのグループ数を `K`、前計算に使う緩和グラフの頂点・辺数を `V′, E′` とすると、逆向き前計算は `O(K(V′ + E′) log V′)`、距離表は `O(KV′)`。グループが固定なら探索中の比較ごとに最大 `K` 個の期間検索で済む。料金境界を検索期間内で整列しておけば、グループ当たり `O(log J)`（`J` は境界数）。バケット内のラベル対の数は別途効くため、計測では比較回数と比較単価を分ける。首都高と料金所は実装負担が中程度。NEXCO の出口判定・走行中の重なり・料金リソースまで絞る部分は中〜高。最初は後続 NEXCO が到達可能なら広い時刻範囲で保守的に調べ、支配できる範囲を段階的に広げる。

### 現行コードを置き換える際の注意点

- `steps_of` は `lab.t - edge.time_min` で辺の開始を逆算する一方、[総当たりの料金再計算](../engine/brute.py)は加算前の時刻を使う。料金所の確定額・ラン料金・表示に同じ辺開始時刻を渡す。異なる浮動小数点時刻を `EPS` で同時刻扱いする短絡を避ける。浮動小数点のまま下限を使うなら、探索の加算順と `datetime` 変換の丸めを包む方向に時間窓を広げ、下限は過大評価しない。誤差を保証できない比較では枝を残す。
- 現行 NEXCO の距離支配には、全対応区分・全対象距離について、同じ割引状態で距離を増やしても最終料金が下がらないという根拠が必要。`validate` の標本検査だけでは保証できない。逓減の各区間で、休日・現行深夜・割引なしの各料金式の単調性を検証する。それまで NEXCO では同一の料金計算状態だけを比較し、浮動小数点の集計が安易に等価とみなせない場合は入力順も含めて同一性を確認する。見直し後は対象距離・時間を `round(..., 6)` で同一視せず、集計値の厳密な一致を使う。距離と割引の関係を証明するまでは成分ごとの大小で落とさない。
- `max_labels` を超えても、厳密モードから時刻境界を無視するモードへ自動で移らない。処理上限を設ける場合は、途中の実行可能解と探索未完了の状態を呼び出し側へ返せる契約にする。完全なパレート集合を返す呼び出しは探索完了を条件とする。

## 3. ほかの方式と前提の変更

| 方式 | 正しさと適用条件 | 計算量の見込み・実装負担 |
| --- | --- | --- |
| 時間拡大グラフ | 時間がもともと共通の刻みに正確に乗るなら、`(構造状態, 料金状態, 時刻)` を頂点とし、走行・ラン終了をそのまま遷移にする。合法 walk と状態グラフ上の経路が対応する。連続時間を整数分等に丸めると料金境界や到着順を変え得る。境界だけで時刻を分割する場合、同じバケットでも後続辺で別の時間帯へ入るため、後続の判定時刻を区間時間だけ逆にずらした境界も必要。見直し後の窓内距離はバケット内で連続的に変わる。 | 正確な刻み幅 `Δ` に対し、最大 `O((T/Δ)S)` の頂点。`S` は時刻を除く状態数で、ラン入口・割引用リソースも含む。到達時刻だけを生成する実装はラベル法に近く、境界を逆伝播する方式もループで分割数が増える。実装負担は高い。 |
| SA/PA で待機を許す | 対象ノードと最大待機時間、ラン継続・割引を定義する。早いラベルが遅いラベルの時刻まで合法に待ち、同じ料金状態で出られる場合は、同じ後続を再現できる。待機中の時間は走行距離や窓内走行時間に加えず、現行の入口〜出口の時間判定には実際の時刻を使う。早い到着によって待機可能時間や割引状態が変わる場合は別状態として扱う。待機なしの総当たりとの等価性は一般に成立せず、待機込みの総当たりを参照にする。 | 許可ノード・候補時刻が増えると分岐も増える。離散入力なら許可された刻みの待機辺で厳密化できる。連続時間では将来イベントから逆算する時刻や、窓内距離・時間上限・円丸めが効く点まで扱う必要がある。利用者に待機場所と待機時間を提示する機能として別段階で設計する。実装負担は高い。 [Dean, 2004](https://doi.org/10.1002/net.20013) |
| 資源制約付き最短路・双方向探索 | 予算を資源としたラベル法と状態緩和の下限は適用できる。双方向にすると、後ろ向きラベルは到着時刻だけでは料金が確定せず、接続時刻ごとの料金と、途中で接続するランの入口・割引状態を保持する必要がある。接続で U ターン・ラン終了条件を検証し、前後を足した料金が全経路の再評価に一致して初めて厳密になる。文献の手法からは状態緩和と下限の考え方を採用する。 | 後半の候補数と可行なラベル対の接続数が効く。全国規模への初手としては、後ろ向きに緩和した時間・料金下限だけを計算する方が実装負担は小さい。双方向での料金結合は高負担。 [Righini・Salani, 2008](https://doi.org/10.1002/net.20212) |

再訪を一律禁止すると、ループによる時刻調整で料金が下がる合法な経路を消すことがある。たとえば休日の料金所が 0 時に 800 円から 400 円へ切り替わるとき、23:58 に JCT `J` に着いてそのまま料金所へ進む経路と、`J → X → Y → J` を 3 分で一周してから通過する経路は、どちらも一般道だけの案より速ければ時間と料金で互いを支配しない。単純路に仕様を変えた場合には、訪問済み集合も支配条件に関わる。走行時間が FIFO であっても、後から同じ辺やランに入る方が料金は下がり得る。 [Dean, *Shortest Paths in FIFO Time-Dependent Networks*](https://people.csail.mit.edu/bdean/tdsp.pdf)

## 4. 実装順と検証

1. **正解の基準を固定する。** 小規模網では `engine/brute.py` を予算で絞り、時間・料金の厳密な組で比較する。テスト入力は時刻を正確に表せる分数または明示した時刻で作り、境界テストでは到着比較の丸めを挟まない。各代表経路を `evaluate` で再評価し、合法性・合計・ラン別料金・料金所時刻を確認する。最初は不明な状態を落とさない参照用モードを用意する。
2. **下限から実装する。** 逆向き時間下限、完成案による大域支配、`t + h(v)` 順の処理を入れる。料金下限は確定額から始め、料金所の逆向き下限、OD・NEXCO の現在ラン下限を個別に追加する。小網で途中ラベルからの全合法続きを列挙し、下限が一度も実値を上回らないことを確認する。完成案と下限が同値、`T` ちょうど、予算ちょうど、複数入口・出口、到達不能も含める。
3. **料金状態とイベント判定を入れる。** 首都高と OD 表、料金所、現行 NEXCO の順に入れ、段階ごとに支配あり・なしと総当たりを照合する。首都高の同一ランが 0 時をまたぐが後に時刻依存イベントがないケースでは支配が働くことを検証する。同じ時間帯にいる二ラベルの後続料金所通過が境目を挟むケースでは、安い方が残ることを検証する。小網では支配で捨てるラベルの全続きを支配側から再生し、個々の完成案でも証明条件を検査できる。
4. **料金・経路制約の境界を固定ケースにする。** 0 時・4 時、休日開始・終了、除外日、アクアラインの方向別時間帯と実施期間、正時以外の改定も直前・ちょうど・直後を比較する。見直し後は窓 22 時・5 時、走行時間上限の 4 時間・4.5 時間、同時刻・同総距離で窓内走行量だけが異なる二経路を入れる。0 時前に走り始めたループが料金を下げる例、直前ノードの違いで可行な後続が変わる例、ラン入口に戻ってもそこで締められない例を含める。プールを混在させた小規模乱数網でも複数の時刻・予算で差分テストを行う。
5. **同一条件で性能を測る。** [規模測定スクリプト](../explore/scale_engine.py)を起点に、500 ノードの再現条件（グラフ、乱数シード、出発・到着条件、料金版）を固定し、2,000〜5,000 ノードと各 10〜20 の入口・出口候補まで増やす。平日昼、日付の直前、4 時前後、休日、改定日前後を含める。現行コードの境界保護あり、時間下限のみ、完成案と料金下限を追加、イベント判定も追加、の順に比較する。前計算と検索時間を分け、冷・温キャッシュの中央値と p95、生成・展開ラベル数、枝刈り理由別件数、最大バケット、最大キュー、ピークメモリを記録する。処理上限に達したケースは未完了として集計する。規模の大きいケースの一致確認には、手順 1 の参照用モードが完走した結果を使う。

ループの多い網では残り時間内の合法な辺列が分岐数と最大区間数に対して指数的に増え得る。下限が緩く、料金状態や到着時刻が互いに支配しない入力では、本方式でも多数のラベルが残る。性能目標の暫定基準は、上記の実用クエリ群で厳密探索をすべて完走し、温キャッシュの p95 が 3 秒以内に収まることとする。冷キャッシュの前計算込み時間も別記する。

## 実装と計測（2026-11-23）

出口候補への逆向き時間下限と、料金所の方向別最低額を使った料金下限を追加した。完成案での枝刈りはキューへの登録時と取り出し時に行う。首都高は後続ランの入口、料金所は料金が確定する辺の始点に絞って時刻境界を確認する。NEXCO は従来の広い判定範囲を使う。上限 `max_labels` を超えた検索は近似モードで再実行し、`Searcher.stats["approximate"]` で識別できる。

`explore/scale_engine.py 500 2000` を同じ Windows 環境の Python 3.12.10 で実行した。各規模でシード 0〜2、各シードにつき水曜 12:00、金曜 23:10、土曜 03:20 の 3 検索、入口・出口はそれぞれ最大 15 候補、`max_labels=50_000`。時間は `search` の実測値で、クエリごとの逆向き下限計算と近似再実行を含む。グラフ生成と `Searcher` 構築時の前計算は計測区間の外にある。計測網の料金プールは NEXCO と首都高で、料金所を含むケースは総当たり照合テストで検証した。

変更前の時間はコミット `e61a10b` から取得し、ラベル数は同じコードの一時コピーに計数だけを加えて取得した。生成数は枝刈り前に作ったラベル、展開数はキューから取り出して後続辺の処理に進んだラベルを数える。近似へ切り替わった場合は、打ち切った厳密探索と近似再実行の両方を合算した。

### 結果

各規模 9 検索（3 シード × 3 出発時刻）。1 検索あたり 180 秒で打ち切る設定にしたが、打ち切りに達した検索はなかった（未完了 0）。時間は完了した検索の平均・最大、生成数は 1 検索あたりのラベル数、近似は `max_labels` を超えて近似モードに切り替わった検索の数。

| ノード数 | コード | 完了 | 平均（秒） | 最大（秒） | 生成ラベル 平均 | 生成ラベル 最大 | 展開ラベル 平均 | 近似 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 500 | 変更前（`e61a10b`） | 9/9 | 20.14 | 135.69 | 60,628 | 273,154 | 21,073 | 2/9 |
| 500 | 変更後 | 9/9 | 0.48 | 2.17 | 18,807 | 66,008 | 6,430 | 1/9 |
| 2,000 | 変更前（`e61a10b`） | 9/9 | 64.58 | 151.42 | 776,594 | 4,017,293 | 265,701 | 5/9 |
| 2,000 | 変更後 | 9/9 | 5.69 | 24.95 | 211,629 | 852,024 | 72,684 | 5/9 |

- 返したパレート集合の件数は、全 18 検索で変更前と同じだった。厳密に完走した検索どうしでは、総当たり照合テストと合わせて同じ答えとみなせる。近似モードどうしは比較の対象外。
- 500 ノードの近似は 2 件から 1 件に減った（シード 2・土曜 3:20 が厳密に完走するようになった）。2,000 ノードは 5 件のまま。厳密探索が `max_labels=50_000` 以内に収まらない検索がまだ多い。
- 速くなった主な理由は、時間下限 `h(v)` による枝刈り（`pruned_time`）と、近似へ切り替える前の打ち切りまでの時間が短くなったこと。計測網はほぼ全域が NEXCO に接続しているため、NEXCO の従来の広い判定が大半の異時刻比較を止めており、首都高・料金所の局所化はこの網ではほとんど効いていない。局所化の効果はテスト（`test_boundary_before_T_but_outside_event_window_allows_dominance`）で確認した。
- 料金所の最低額による料金下限と完成案での枝刈りは、計測網に料金所がなく完成案も一般道案以外は少ないため、`pruned_completed` は最大 1,931 件にとどまる。
- 性能目標（実用クエリ群で厳密探索をすべて完走し、温キャッシュ p95 が 3 秒以内）は未達。次は NEXCO のイベント判定の局所化（出口日の休日判定・ランの 0〜4 時の重なり）が必要。

### 検証

- 総当たりとの照合テストを追加した（`engine/tests/test_exact_search.py`）。料金プールを混ぜた小規模乱数網（12 シード × 7 出発時刻、各フロントの料金ちょうど・1 円不足の予算も照合）、途中ラベルからの全合法続きに対して時間下限・料金所下限が実値を超えないこと、首都高の同一ランが 0 時・4 時・改定時刻をまたいでも支配が働くこと、同じ時間帯の二ラベルの後続判定（首都高入口・アクアライン料金所・NEXCO 入口）が境目を挟むと安い方が残ること、T ちょうど・T の直前、浮動小数点の加算順で 1 ulp ずれるケース、予算ちょうど。
- 各枝刈りを無効にしても、総当たり照合の結果は変わらない（失敗するのは枝刈り件数を確かめるテストだけ）: 時間下限、完成案による枝刈り、料金所の料金下限、予算での枝刈り、取り出し時の再判定、首都高・料金所の判定範囲の局所化。
- 各規則をわざと誤らせると、いずれかの照合テストが失敗する: 時間下限の 1/4 分の過大評価、浮動小数点の誤差幅の除去、完成案の料金を見ない・時刻をずらす、料金所の下限を平日額にする・二重に数える、予算ちょうどを落とす、イベント判定の省略・B の時刻で判定・境目ちょうどの扱い・残り時間の過大評価、首都高の再進入を数えない・直前プールを取り違える、NEXCO の従来判定の省略、最後の境目を 1 時間早く見る、同額の遅い完成案を残す、首都高の状態鍵から深夜フラグを外す。
- レビューで直した点: 厳密モードの距離（区分別）の支配判定が `1e-9` の誤差を許していた（わずかに長い距離で料金の丸めが変わり得る）ので厳密な比較にした。見直し後の深夜割引の状態鍵が窓内距離・時間を `round(..., 6)` で同一視していたので、集計値の厳密な一致にした。

### 残る懸念

- NEXCO が到達可能な範囲では異時刻の比較がほぼ止まるため、全国規模では近似モードへの切り替えが多い。近似モードの結果は境目の前後で安い候補を落とし得る。
- 浮動小数点の誤差幅（`_forward_time_error`）は区間時間の最小値から加算回数を上から抑えている。ゼロに近い区間時間があると下限が無効になり（安全側）、枝刈りが効かなくなる。
- 料金所の最低額は `flat_gate` とアクアラインだけが既知。ほかの料金関数は 0 円（安全側）になる。

## 現行 NEXCO の時刻境界の局所化

後続ランの時刻範囲は、現在のノードとプールから次に NEXCO へ入るまでの時間下限と、NEXCO ランを閉じてから目的地へ着くための時間下限で絞る。ラン終了の候補は、検索で使う出口と別のプールへの乗り継ぎ。現在ランでは、入口日が休日割引の条件を満たせば出口日の切り替えは料金に影響せず、一度 0〜4 時に重なれば深夜割引の時刻条件も消えない。現在ランの終了時刻が影響する条件だけを確認する。見直し後の深夜割引が有効になり得る範囲では、異なる時刻での比較を保守的に抑える。

同じ Docker 環境で `python explore/scale_engine.py 500 2000 --cap 45` を変更前後それぞれ実行した。検索は両方とも全件完了し、パレート集合の件数は全 18 件で一致した。

| ノード数 | 変更前の近似 | 変更後の近似 | 平均秒（前 → 後） | 生成ラベル平均（前 → 後） |
| --- | --- | --- | --- | --- |
| 500 | 1/9 | 1/9 | 0.47 → 0.54 | 18,807 → 24,177 |
| 2,000 | 5/9 | 3/9 | 4.90 → 5.04 | 211,629 → 207,884 |

2,000 ノードの土曜 3:20 の検索 2 件が厳密モードで完了した。一部の近似に入る検索では厳密探索中の生成ラベル数が増え、平均所要時間は両規模で微増した。現在ランの終了が午前 0 時をまたぐ場合と、成立済みの割引条件が午前 4 時を過ぎても維持される場合を総当たりと照合した。
